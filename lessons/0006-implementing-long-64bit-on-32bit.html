Implementing long: 64-bit on 32-bit Hardware

The ARM encoder has codeLong* stubs everywhere. Here's the mental model that turns them into real code — one 64-bit value, three ways to compute with it.

One idea first

Your target (32-bit ARM) has no 64-bit registers. So a long — which you already know is a two-slot JVM type (Lesson 2) — must live in two 32-bit words. jcore calls this pair a Reg64, with a low and a high half (Reg64.java:17-18):

value = [ high word ][ low word ]      // two 32-bit registers
        // Reg64.eax = { low: eax, high: edx }   (Reg64.java:13)
        // Reg64.ebx = { low: ebx, high: ecx }

Now the hard part. A 32-bit CPU computes with one word at a time. When the low words add and overflow, the overflow has to reach the high words. The CPU's carry flag is the bridge — and everything about long support is really about how each operation treats that bridge.

The three decomposition patterns

Every long operation in jcore is one of three patterns. Find the pattern, and you know how to write it on ARM.

Pattern 1 — Word-at-a-time: bitwise ops (no carry)

AND/OR/XOR process each bit independently. No word depends on another, so you just run the 32-bit instruction twice — order doesn't even matter. IMBitAnd.translate(Reg64) (IMBitAnd.java:86-102):

lOpr.translate(result);
reg = regs.chooseLongRegister(result);     // scratch pair
rOpr.translate(reg);
code.andl(reg.low,  result.low);           // low  word: result.low  &= reg.low
code.andl(reg.high, reg.high);             // <-- see the bug-hunt below

Pattern 2 — Carry-chained: add, sub, negate

The core idea of all multi-word arithmetic:

IMAdd.translate(Reg64) (IMAdd.java:212-230) does exactly this:

code.addl(reg.low,  result.low);     // low  words add  → sets carry
code.adcl(reg.high, reg.high);       // <-- and here's the other bug-hunt

Subtraction is the same shape with borrow: SUBS then SBC (IMSub.java:196-214, calls subl/sbbl). Negation is negl lo; adcl 0, hi; negl hi (IMNeg.java:85-97).

Pattern 3 — Runtime helper call: mul, div, rem, shifts, lcmp

These are too expensive to inline (64×64 multiply is four 32-bit multiplies plus carries; division is a whole algorithm). The IA32 backend sidesteps entirely — it calls a helper routine. ExecEnvironmentIA32.codeLongMul (ExecEnvironmentIA32.java:1306):

lOpr.translate(reg); frame.push(reg);          // push first long arg
rOpr.translate(reg); frame.push(reg);          // push second long arg
regs.saveIntRegister();
code.call(new LongArithmeticSTEntry(LongArithmeticSTEntry.MUL));   // runtime helper
// result comes back in the eax/edx pair (Reg64.eax)

The same shape appears for DIV, REM, SHL, SHR, USHR and LCMP (ExecEnvironmentIA32.java:1332, 1358, 1385, 1411, 1437, 1472). The helper is a runtime routine (LongArithmeticSTEntry.java:10) — jcore writes the value onto the frame stack, calls, reads the pair back.

The ARM twist: flags are opt-in

Here is the trap that makes a copy-paste port fail. On x86, every ALU instruction writes the flags. On ARM, a data-processing instruction writes the flags only if the S bit (bit 20) is set — ADDS sets carry, plain ADD does not.

Now read your encoder again. add and sub pass s=false (BinaryCodeDynamicARM.java:464-487). The low-word add of a 64-bit chain must set the carry — so it needs a flag-setting variant. And the carry-consuming instructions are separate opcodes, not the same opcode reading a flag:

Operationx86 (what IM nodes call)ARM encoding neededEncoder today
low-word addaddlADDS (S bit set)add, s=false — gap
high-word addadclADC (op 0x5, reads carry)DP_ADC defined :135, adc is a stub :615 — gap
low-word subsublSUBS (S bit set)sub, s=false — gap
high-word subsbblSBC (op 0x6, reads borrow)not present — gap
negate pairnegl+adclRSBS+RSC (ops 0x3/0x7)DP_RSB exists, no rsc — gap

Meanwhile the helper-call pattern needs no new arithmetic opcodes at all — call(SymbolTableEntryBase) already emits a relocatable BL (BinaryCodeDynamicARM.java:247). Pattern 3's real cost is writing the ARM-side long-arithmetic routines.

Before you write a line: bug-hunt the reference

Two calls above have a suspicious operand. Read them in context:

  • IMAdd.java:225 — code.adcl(reg.high, reg.high). adcl(src, des) means des += src + carry (BinaryCodeIA32.java:986). So this adds reg.high to itself and never touches result.high. The high word of the addend is lost. It should be adcl(reg.high, result.high).
  • IMBitAnd.java:97 — code.andl(reg.high, reg.high) is a no-op (x &= x), dropping result.high. Should be andl(reg.high, result.high). IMBitOr/IMBitXor are likely the same.

These are in the reference x86 backend — so 64-bit path has clearly never been exercised there, and you cannot trust it as a source of truth. When you port the carry chain to ARM, verify the semantics yourself with a 2-3 line test program rather than copying.

What "implement long support" means here

Everything before Act 4 already works — the IM nodes dispatch by datatype to translate(Reg64), which reaches your codeLong* stubs or the inline addl/adcl/… calls (IMNode.java:297-322). Your job is the encoder, in this order:

  1. Close the naming seam (from Lesson 5): the IM nodes call x86 names — addl, adcl, subl, sbbl. Add those method names to BinaryCodeDynamicARM (thin shims over add/adc/…).
  2. Add flag-setting low words: the carry chain needs ADDS/SUBS for the low word — currently add/sub pass s=false.
  3. Implement adc and sbc: DP_ADC already exists (:135); add DP_SBC = 0x6 and the sbc method.
  4. For the helper-call ops (mul/div/rem/shifts/lcmp): wire your codeLong* stubs to the existing call/stack ABI, and write the ARM long-arithmetic routines.
