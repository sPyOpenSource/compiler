Lesson 1: Measure Before You Optimize

Mission tie-in: You're building a JIT compiler. Profiling is how you know which optimizations actually matter — and whether your compiler's output is faster.

Why This Lesson

The single biggest mistake in performance optimization is optimizing without measuring. Human intuition about bottlenecks is notoriously wrong — even experts guess incorrectly >50% of the time. Before you change a single line of code, you need data.

Golden Rule: Profile first. Optimize second. Verify third.

What Profiling Tells You

A profiler answers three questions:

  1. Where is time spent? (Which functions, lines, instructions)
  2. Why is it slow? (Cache misses, branch mispredictions, memory bandwidth, lock contention)
  3. How much can it improve? (Upper bound on speedup via Amdahl's Law)

Types of Profiling

Your First Profile: perf

On Linux, perf is the standard sampling profiler. Here's the workflow:

# 1. Compile with debug symbols (no -O3 yet — we want readable profiles)
gcc -O2 -g -fno-omit-frame-pointer my_program.c -o my_program

# 2. Record a profile (run for ~10-30 seconds)
perf record -g --call-graph dwarf ./my_program

# 3. Analyze
perf report          # TUI: navigate with arrows, Enter to expand
perf report --stdio  # Text output for scripts
perf script          # Raw samples for FlameGraphs
Critical: Always compile with -fno-omit-frame-pointer and -g. Without frame pointers, perf can't unwind the stack — you'll see ??? instead of function names.

Reading a perf report

Key columns:

  • Overhead % — percentage of samples in this function
  • Children % — percentage in this function plus its callees
  • Self % — percentage only in this function (not callees)

Focus on high Self % — that's where the CPU actually executes your instructions.

Hardware Counters: The "Why"

Sampling tells you where. Hardware counters tell you why:

# Overall pipeline health
perf stat ./my_program

# Specific events
perf stat -e cache-misses,cache-references,branch-misses,branch-instructions ./my_program

# Per-function breakdown
perf record -e cache-misses -g ./my_program
perf report

Key metrics to watch:

MetricHealthyConcerningLikely Cause
IPC (Instructions Per Cycle)> 1.0 (modern CPUs)< 0.5Stalls: cache misses, dependencies
Branch miss rate< 1%> 5%Unpredictable branches
LLC miss rate< 5%> 20%Working set > cache, poor locality
Cycles stalled (frontend/backend)LowHighFrontend: decode/ICache; Backend: data deps

Microbenchmarking: Comparing Alternatives

When you have a hot function and want to test a faster version, use Google Benchmark:

#include 

static void BM_StringCopy(benchmark::State& state) {
  std::string src(state.range(0), 'x');
  for (auto _ : state) {
    std::string dst = src;  // measured operation
    benchmark::DoNotOptimize(dst);
  }
}
BENCHMARK(BM_StringCopy)->Arg(16)->Arg(256)->Arg(4096);

BENCHMARK_MAIN();
Key benchmark practices:
  • DoNotOptimize prevents the compiler from deleting your work
  • Use Arg / Range to test multiple input sizes
  • Run with --benchmark_repetitions=10 for statistical significance
  • Pin CPU frequency: sudo cpupower frequency-set -g performance

Flame Graphs: Visualizing the Stack

Flame graphs turn perf script output into an intuitive visualization:

# Install flamegraph.pl (from Brendan Gregg's repo)
git clone https://github.com/brendangregg/FlameGraph
export PATH=$PATH:$(pwd)/FlameGraph

# Generate SVG
perf script | flamegraph.pl > profile.svg

Reading flame graphs:

  • X-axis = stack depth (not time!), sorted alphabetically
  • Width = proportion of samples
  • Wide plateau at top = hot function
  • Color = usually random/hue by function name (helps visually group)

Quick Quiz

You profile a program and see Function A at 40% Self overhead, Function B at 30% Self overhead. Function A calls Function B. Where should you optimize first?

Your perf stat output shows IPC = 0.3 and high "backend stalled cycles". What's the most likely bottleneck?

Exercise: Profile Something Real

  1. Pick a small C/C++ program you've written (or write one: e.g., matrix multiply, string parsing, sorting)
  2. Compile: gcc -O2 -g -fno-omit-frame-pointer prog.c -o prog
  3. Run: perf record -g ./prog
  4. Run: perf report --stdio | head -50
  5. Identify the top 3 functions by Self %
  6. Run: perf stat ./prog and note IPC, cache-miss rate, branch-miss rate
