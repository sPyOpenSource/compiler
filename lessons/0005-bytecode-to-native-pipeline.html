Bytecode → Native Code: The Pipeline

How a stack-based class file becomes register-based machine code — traced through jcore's actual source.

One idea first

JVM bytecode is written for a stack machine: iadd pops two values, pushes one. Native code is written for a register machine: ADD R0, R0, R1. Everything between bytecode and native code is an answer to one question — how do we turn stack discipline into registers? jcore answers it in four acts.

Follow one instruction: iadd

Take the body iload_1; iload_2; iadd; istore_3. Watch iadd move through each act.

Act 1 — Bytecode → IM graph

CodeContainer.readBCInstruction() (CodeContainer.java:207) walks the bytecode stream and creates one IM node per instruction. For iadd it builds new IMAdd(this, current, ip) (CodeContainer.java:527). A second pass merges these into basic blocks (straight-line runs with one entry and one exit).

Then the key step: VirtualOperantenStack (CodeContainer.java:286) simulates the bytecode operand stack. When IMAdd's processStack() runs, it pops two operands and pushes itself (IMBinaryOperator.java:49):

rOpr = stack.pop();   // iload_2
lOpr = stack.pop();   // iload_1
stack.push(this);     // now a tree: IMAdd(iload_1, iload_2)

The linear bytecode stack has become an expression tree. This is the whole trick of Act 1.

Act 2 — Optimize the graph

CodeContainer.constant_forwarding() (CodeContainer.java:1062) runs folding and forwarding on every basic block. For IMAdd (IMAdd.java:45) this folds x + 5 + 3 into x + 8 and swaps operands so a constant lands on the right — a detail Act 3 depends on.

Act 3 — Instruction selection + register allocation

CodeContainer.translate() (CodeContainer.java:1079) walks the basic blocks and calls node.translate(Reg) on each. This is where the tree is turned into instructions — but note what it emits: it calls methods on a code object, not raw bytes.

// IMAdd.translate(Reg result)  — IMAdd.java:107 (abridged)
lOpr.translate(result);
reg = regs.chooseIntRegister(result);   // allocate a scratch register
rOpr.translate(reg);
code.addl(reg, result);                 // <-- selection: an add instruction
regs.freeIntRegister(reg);

RegManager hands out registers; MethodStackFrame decides where locals and temps live. If the right operand is a constant, the same method emits code.addl(value, result) — or code.incl(result) for +1 (IMAdd.java:153–161). Small, target-neutral optimizations already live here.

Act 4 — The encoder: calls → bytes

code is a BinaryCodeIA32 (CodeContainer.java:111). Its addl(...) (BinaryCodeIA32.java:797, 809) writes the x86 opcode bytes into a growing byte[]. Its ARM twin is BinaryCodeDynamicARM, where add(Opr, Reg) (BinaryCodeDynamicARM.java:464) emits dpr(C_AL, DP_ADD, …) / dpi(...) — the ARM encodings you have been implementing.

Unresolved jumps, method calls and constant-pool references are recorded as SymbolTableEntryBase objects; getOldBinaryCode() resolves them and wraps everything in a BinaryCode. From there it's packaged into the .jll/.jln files you studied in Lesson 4.

The insight: BinaryCode is the seam

The IM nodes never emit machine code. They call code.addl(...), code.incl(...), code.movl(...), code.cmpl(...) — a method interface, not x86. BinaryCodeIA32 happens to implement it with x86 bytes; BinaryCodeDynamicARM is the ARM implementation of the same contract.

Two things currently keep the ARM encoder out of the loop:

  1. Names. The IM nodes call addl/movl/incl; BinaryCodeDynamicARM implements add/mov/… — the method names don't line up yet.
  2. Wiring. CodeContainer hard-codes code = new BinaryCodeIA32() (CodeContainer.java:111). The codeType() switch in StaticCompiler (StaticCompiler.java:84) picks the exec environment, not the encoder.

So plugging ARM in means: match the method interface (or extract a real interface from BinaryCodeIA32), then swap the constructor. Everything before Act 4 — the graph, the optimizations, instruction selection — is architecture-independent already.
