Identifying GUI Improvements

Lesson 3 of ? — Mission: AOT Compilation

You have a working Swing launcher for the compiler in src/gui/. It compiles, runs, and displays output. But several parts are broken or half-finished. This lesson teaches you how to systematically analyze a GUI codebase and prioritize fixes.

The audit: read the code with fresh eyes

Start by reading src/gui/Compiler.java (385 lines). It has four source files total. Ask these questions:

1. Does each component do what its name says?

ComponentName saysActually doesVerdict
"Open" buttonOpen a projectRuns flatpak run org.apache.netbeansLabelled wrong — it launches an IDE, not "Open"
"Kernel IDE" buttonEdit kernelRuns flatpak run io.atom.AtomSame pattern: launches Atom editor
"Show Logging" buttonShow log outputStarts OutputReader thread polling /home/spy/output.txtStarts a background reader, but log output is already being captured via LogOutputStream
Finding #1: Button labels that lie. "Open" doesn't open — it launches NetBeans. "Show Logging" implies a toggle, but it starts a thread that never stops.

2. Is the data flow correct?

openMenuItemActionPerformed (line 247) uses JFileChooser.showSaveDialog instead of showOpenDialog. That's the "Save As" dialog, not "Open File". It still works (you can select files) but it confuses the user.

Worse: after reading the file line-by-line into List<String> liststrings (line 258-262), the code completely ignores the data and hardcodes four strings:

strings[0] = "Zero";
strings[1] = "OS";
strings[2] = "testOS";
strings[3] = "AIZero";
Finding #2: Dead code path. The file is read but its contents are never used. The project list always shows the same four hardcoded entries regardless of which file you open.

3. Are there competing mechanisms?

Output reaches the JTextArea through two different paths:

  • LogOutputStream (line 288-290): installed via System.setOut() when a project is opened. Captures all System.out writes and appends them to the JTextArea via SwingUtilities.invokeLater. This is clean.
  • OutputReader (line 327): spawned as a background thread when "Show Logging" is clicked. Polls /home/spy/output.txt every 500ms and appends lines. This is fragile (hardcoded Linux path, busy-polling).
Finding #3: Two logging systems, one fragile. LogOutputStream works well; OutputReader should be removed.

Prioritizing fixes

Not every bug deserves the same attention. A useful framework:

P0 (Showstopper)
Core functionality is broken. The feature doesn't do what it says.
→ Your "Open" button being a NetBeans launcher? The project list not showing file contents? These are P0.
P1 (Major)
Works but poorly. Missing feedback, confusing behavior, fragile paths.
→ No compile progress indicator. Hardcoded flatpak/Linux paths. The save dialog instead of open dialog.
P2 (Minor)
Annoyance or polish. Non-functional menu items, inconsistent naming.
→ Cut/Copy/Paste doing nothing. "Show Logging" button name.
P3 (Cosmetic)
Won't fix unless you're already changing that area.
→ Button sizing, font choices, window title.

The NetBeans form problem

The initComponents method (line 41-221) is auto-generated by the NetBeans GUI Builder. The comment says "WARNING: Do NOT modify this code." If you edit it by hand and then open the .form file in NetBeans, it will overwrite your changes.

Two approaches:

  • Detach from NetBeans: Delete the .form file and hand-code the layout. You gain full control but lose visual editing.
  • Stay with NetBeans: Only edit in the .form file or the NetBeans designer. Never touch initComponents by hand.

For the fixes suggested in this lesson, you can work entirely in the action listener methods and the helper classes — no layout changes needed. You never need to touch initComponents.

Tangible win: your improvement map

You can now look at any GUI code and systematically find:

  1. Naming lies — buttons/actions that don't match their labels
  2. Broken data flow — values computed but ignored; wrong dialog types
  3. Competing mechanisms — two ways to do the same thing, one fragile
  4. Dead UI — components with no listeners, unreachable paths
  5. Hardcoded assumptions — paths, commands, file locations specific to one machine

Your compiler GUI has at least one of each category — a rich set of concrete problems to practice on.
