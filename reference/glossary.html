Glossary: AOT & JIT Compilation

AOT (Ahead-of-Time) compilation
Translating source or bytecode into machine code before execution, usually at build time. Produces a standalone executable. Lesson 1
JIT (Just-in-Time) compilation
Translating bytecode to machine code during execution, typically for frequently-executed ("hot") methods. The JVM's default mode. Lesson 1
Closed-world assumption
The assumption that all reachable code is known at build time. AOT compilers use this to devirtualize calls, inline aggressively, and eliminate dead code. Breaks with reflection or dynamic class loading. Lesson 1
Warmup
The period during which a JIT-compiled application transitions from interpreted execution to fully optimized native code. AOT binaries skip warmup entirely. Lesson 1
PGO (Profile-Guided Optimization)
A two-phase AOT strategy: (1) build an instrumented binary and run it on representative data to collect profiles; (2) rebuild with those profiles guiding optimization decisions. Bridges the JIT/AOT gap. Lesson 1
Substrate VM
The lightweight runtime embedded in GraalVM native images. Provides memory management (GC), thread scheduling, and exception handling — but no bytecode interpreter or JIT compiler. Lesson 1
Points-to analysis
A static analysis that determines which objects a reference variable can point to. Used by AOT compilers under the closed-world assumption to enable devirtualization and escape analysis. Lesson 1
Devirtualization
Replacing a virtual method call (which requires a vtable dispatch) with a direct call to a known implementation. Easy under closed-world; requires guards in a JIT. Lesson 1
Deoptimization
A JIT mechanism that rolls back optimized code when its speculative assumptions (e.g., "this call is monomorphic") prove wrong. Not available in AOT — the compiled code is fixed. Lesson 1
Native image
A self-contained executable produced by GraalVM's AOT compiler. Includes application code, JDK classes, and Substrate VM — but no JVM. Lesson 1
JVM Slot
The basic unit of storage on the JVM operand stack and in local variables. Typically 32 bits wide. Lesson 2
Two-Slot Type
Types (long, double) that occupy two consecutive slots on the stack. This requires special handling in the compiler's stack simulation. Lesson 2
XMM Register
Specialized 128-bit registers used by x86 for floating-point (SSE) and SIMD operations. Lesson 2
GPR (General Purpose Register)
Standard CPU registers (like RAX, RBX) used for integer arithmetic and memory addresses. Lesson 2
SwingUtilities.invokeLater
Ensures a Runnable executes on the Event Dispatch Thread (EDT). All Swing component updates must happen on the EDT to avoid race conditions. Lesson 3
EDT (Event Dispatch Thread)
The single thread responsible for all Swing event handling and component rendering. Long-running tasks (like compilation) must run on a background thread, not the EDT. Lesson 3
SwingWorker
A utility class for running background tasks in Swing and publishing intermediate results back to the EDT. Preferred over raw Thread for UI-triggered work like compilation. Lesson 3
JFileChooser (showOpenDialog vs showSaveDialog)
showOpenDialog presents a file-open dialog; showSaveDialog presents a file-save dialog. Using the wrong one confuses users (e.g., "Save" button on an "Open" dialog). Lesson 3
NetBeans GUI Builder (.form file)
An XML file produced by NetBeans' visual form editor. Paired with auto-generated initComponents() code. Hand-editing the Java is overwritten if the form is re-opened in the builder. Lesson 3
LogOutputStream
A custom OutputStream subclass that redirects System.out to a JTextArea via SwingUtilities.invokeLater. Clean pattern for console-in-GUI. Lesson 3
Busy-polling
A loop that checks for new data at fixed intervals (e.g., every 500ms). Wastes CPU and introduces latency. Avoid in favor of event-driven mechanisms. OutputReader in this codebase uses this pattern. Lesson 3
.jll (Java Library Linkable)
Binary file containing native machine code and class/method metadata for a domain. Used as the primary AOT artifact. Lesson 4
.jln (Java Linker Notification)
Binary file containing resolved VTable information for a domain. Used by the runtime linker to map virtual method calls to their native implementations. Lesson 4
IM graph (intermediate code graph)
The tree of IM nodes (e.g., IMAdd) produced from bytecode. A stack machine flattened into expression trees. Built by CodeContainer.readBCInstruction and the VirtualOperantenStack. Lesson 5
Basic block
A straight-line run of instructions with one entry and one exit — the unit the code generator walks. Lesson 5
VirtualOperantenStack
jcore's simulation of the JVM operand stack. Its processStack method pops operands and builds expression trees during the parse pass. Lesson 5
Instruction selection
The stage where each IM node's translate(Reg) decides which machine instructions to emit — as calls like code.addl(...). Target-neutral in jcore. Lesson 5
Register allocation
Deciding which physical CPU registers hold which values. In jcore this is RegManager, driving the translate(Reg) calls. Lesson 5
Instruction encoding
Turning code.*() calls into raw machine bytes. BinaryCodeIA32 encodes x86; BinaryCodeDynamicARM encodes ARM. This is where the ARM backend work lives. Lesson 5
Relocation (symbol table entry)
An unresolved address (jump target, call, constant-pool ref) recorded during encoding and patched later. SymbolTableEntryBase subclasses in jcore. Lesson 5
Register pair (Reg64)
Two 32-bit registers holding the low and high halves of one 64-bit value. Reg64.low / Reg64.high; jcore's predefined pairs are eax/edx, ebx/ecx, esi/edi. The codegen form of a two-slot JVM type. Lesson 6
Carry flag
The condition-code bit that records overflow out of the low word of an addition (and borrow in subtraction). It is the bridge between words in multi-word arithmetic. Lesson 6
Carry-chained arithmetic
Computing with words larger than the register: low word first (sets the carry flag), then high word(s) with an add-with-carry (adcl/ADC) or subtract-with-borrow (sbbl/SBC) instruction. jcore uses this for long add, sub, negate. Lesson 6
Word-at-a-time operation
A 64-bit operation that runs the same 32-bit instruction on each word independently, with no carry or ordering dependency — e.g. bitwise AND/OR/XOR. Lesson 6
S bit (ARM condition-code flag)
Bit 20 of an ARM data-processing instruction. On x86 every ALU op sets flags; on ARM flags update only when S is set (ADDS vs ADD). This is the trap when porting x86 carry chains to ARM. Lesson 6
LongArithmeticSTEntry
jcore's symbol-table entry for the runtime long-arithmetic helper (MUL, DIV, REM, SHL, SHR, USHR, CMP). The IA32 backend pushes operands and calls it instead of inlining these complex ops. Lesson 6
